# Деплой photos-api в Yandex Cloud Functions

Это основной backend, который подписывает presigned-ссылки на Yandex Object
Storage вместо приложения. Использует те же сервисные аккаунты и секрет
`photos-backend-secrets`, что уже были созданы для зонда — новых секретов
заводить не нужно.

Готовый архив: `backend/photos-api/dist/photos-api.zip` (~660 КБ).

## 1. Создание функции

1. Yandex Cloud Console → **Cloud Functions** → «Создать функцию».
2. Имя: `photos-api`.
3. В редакторе функции:
   - **Среда выполнения:** Node.js, самая новая из доступных (18 и выше).
   - **Способ:** ZIP-архив → выберите `backend/photos-api/dist/photos-api.zip`.
   - **Точка входа:** `index.handler`
   - **Таймаут: 30 секунд.**
   - **Память: 512 МБ.**
   - **Сервисный аккаунт:** `photos-function-runtime` (тот же, что у зонда).
   - **Переменные окружения** (обычные, не секреты):
     - `S3_BUCKET` = `app-remont-photos`
     - `S3_ENDPOINT` = `storage.yandexcloud.net`
     - `S3_REGION` = `ru-central1`
     - `FIREBASE_PROJECT_ID` = `remont-76b60`
   - **Секреты из Lockbox** (тот же секрет `photos-backend-secrets`, что и у
     зонда — три записи, каждая привязывается к одноимённой переменной):
     `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `FIREBASE_SA_JSON`.
   - **Публичность:** НЕ включать. Доступ будет только через API Gateway (см. ниже).
4. «Сохранить изменения», дождаться готовности новой версии.

## 2. Быстрая проверка без API Gateway (необязательно)

Функцию можно дёрнуть напрямую из вкладки «Тестирование», без реального
Firebase ID token — только чтобы убедиться, что она вообще запускается и
правильно возвращает ошибки. Тело теста (это JSON самого `event`, а не тела
HTTP-запроса):

```json
{
  "httpMethod": "POST",
  "path": "/get-urls",
  "headers": {},
  "body": "{}"
}
```

Ожидаемый результат: `statusCode: 401` (нет токена) — это значит, что функция
работает и корректно отклоняет запрос без авторизации. Полноценно
эндпоинты можно проверить только с настоящим Firebase ID token настоящего
пользователя приложения — это будет частью следующего шага (переключение
`storage_service.dart` на backend).

## 3. API Gateway (когда дойдёте до этого шага — не обязательно сейчас)

Функции нужен один HTTP-вход с тремя маршрутами, все — `POST`, все ведут в
`photos-api` (интеграция `cloud_functions`, сервисный аккаунт шлюза с ролью
`functions.functionInvoker`):

- `POST /put-url`
- `POST /get-urls`
- `POST /delete`

Функция сама разбирает `event.path` и определяет маршрут по последнему
сегменту — конкретный формат спецификации OpenAPI для Yandex API Gateway
подготовим отдельным шагом, когда будем переключать приложение.

## 4. Как читать ошибки

Все три эндпоинта отвечают одинаковым форматом:
`{ "error": "<код>", "message": "<человеко-читаемое сообщение>" }`.

| HTTP | error | Когда |
|---|---|---|
| 401 | `unauthenticated` | Нет заголовка `Authorization: Bearer ...` или токен невалиден/просрочен |
| 403 | `permission_denied` | Токен верный, но у пользователя нет прав на этот путь/файл (в т.ч. оплаченный чек) |
| 400 | `invalid_argument` | Неверный формат тела запроса или `storagePath` |
| 404 | `not_found` | Неизвестный маршрут |
| 409 | `already_exists` | put-url: файл с таким `storagePath` уже есть в бакете (защита от затирания) |
| 502 | `storage_error` | Yandex S3 ответил неожиданным статусом (само по себе не должно происходить) |
| 500 | `internal` | Непредвиденная ошибка — подробности только в логах функции, не в ответе |

В логах (Cloud Logging) секретов нет — туда пишутся только маршрут, uid,
код ошибки и статус.
