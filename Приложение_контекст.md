## Архитектура (гибрид — важно!)
- **Firestore + Auth** на Firebase (проект `remont-76b60`, бесплатный Spark, без карты).
- **Фотографии** — на **Yandex Object Storage** (S3-совместимое), бакет `app-remont-photos`
  (ПРИВАТНЫЙ), endpoint `storage.yandexcloud.net`, регион `ru-central1`.
- Причина гибрида: Firebase Storage требует платный Blaze с зарубежной картой (из РФ не оплатить).
- **VPS НЕ нужен** для работы — приложение ходит только в Firebase + Yandex (оба облачные, 24/7).
- Роли: **owner** (директор) / **manager** (прораб) / **worker** (подрядчик) / **client**
  (заказчик) / user.

## Как устроены данные и права
- Компания (`companies/{id}`) + членство (`companies/{id}/members/{uid}` с `active: true` boolean,
  `role: "owner"` string). `createCompany` создаёт компанию + членство владельца АТОМАРНО (batch).
- Объекты: `projects/{id}` (поля: ownerId, companyId, participantIds, workerIds, managerIds,
  clientIds, status).
- Этапы: `projects/{id}/stages/{stageId}` (модель **Stage**: title, status, assignedUserIds,
  receiptsCount, receiptsTotal). Есть легаси-модель RepairStage над той же коллекцией.
- Чеки/расходы: `projects/{id}/expenses/{id}` + зеркало в `stages/{sid}/photos/{id}` (type:
  receipt) — ОБА хранят сумму, менять СИНХРОННО в одном batch.
- Фото: `projects/{id}/stages/{sid}/photos/{id}`. Сумма по этапу (receiptsTotal) — денормализована,
  меняется через FieldValue.increment; по объекту — считается на лету из стрима.
- **firestore.rules** — правила доступа, автотесты в `rules-tests/` (29/29 passing). Права:
  canReadProject / canManageProject / isAssignedStageWorker.
- Оплаченный чек (`isPaid == true`) ЗАМОРОЖЕН для ВСЕХ (включая владельца) — и в правилах, и в UI.
  Неоплаченный: автор-подрядчик правит/удаляет свой; владелец/менеджер — любой.

## Безопасность / секреты (ВАЖНО)

## ТЕКУЩАЯ ЗАДАЧА: миграция подписи S3 на backend (Yandex Cloud Functions)

**Зачем:** (1) убрать S3-ключ из APK (сейчас компилируется в libapp.so, извлекаем — риск);
(2) ПОЧИНИТЬ БАГ: presigned GET-ссылки живут ровно 7 дней (storage_service.dart:80), генерируются
1 раз при загрузке, сохраняются в Firestore, при показе НЕ перевыпускаются → фото старше 7 дней =
битая картинка навсегда. Данные целы (файлы в S3, storagePath сохранён).

**РЕШЕНИЯ ПРИНЯТЫ (не переобсуждать):**
1. Бакет приватный.
2. v1.0 на модерации, юзеров НЕТ → БЕЗ двойного режима, ключ меняем сразу.
3. Права на backend — ВАРИАНТ A: Firebase Admin SDK + сервисный аккаунт (роль datastore.viewer).
4. Автор-подрядчик может удалять файл своего неоплаченного чека (x-amz-meta-uploader).
5. Платформа — **Yandex Cloud Functions** (Node.js, handler), НЕ Serverless Containers.
   Стратегия — ВАРИАНТ Б: сразу полный backend (чинит и баг, и безопасность).

**Архитектура backend:** приложение шлёт запрос с Firebase ID token → функция verifyIdToken →
проверяет ПРАВА (повтор логики firestore.rules через Admin SDK, читая документ проекта) → подписывает
presigned URL своим ключом (только на сервере) → возвращает. Эндпоинты: **put-url** (загрузка),
**get-urls** (ПАКЕТНЫЙ, до ~50 путей — иначе сетка из 30 фото = 30 запросов), **delete**.
КРИТИЧНО: без проверки прав backend = дыра (любой авторизованный получит чужие фото). Тест-матрицу
из rules-tests перенести в тесты backend. Кэш прав ≤30 сек.

**В приложении:** сохранить публичный API StorageService, внутри — getIdToken() + HTTP к backend.
Удалить aws_signature_v4/aws_common, S3-ключи из dart-define. Нужен виджет-резолвер (по storagePath
пакетно просит свежие URL, кэш в памяти) + `CachedNetworkImage(cacheKey: storagePath)` — иначе фото
перекачиваются при каждом показе. Старые записи без storagePath заполнить разовым скриптом.

**Развёртывание (консоль Яндекса):** новый сервисный аккаунт `photos-signer` (роль storage.editor
только на бакет) + новый ключ = РОТАЦИЯ (старый ключ засвечен в APK). Секреты в Lockbox. Функция
Node.js, API Gateway для HTTP. Firebase: сервисный аккаунт с datastore.viewer, скачать JSON.
Проверить доступность googleapis из Yandex Cloud (для verifyIdToken).

**Существующий backend/** (Express в Docker) как есть под Cloud Functions НЕ годится (нужен
handler, не слушающий порт), но переиспользуется: firebase-admin init, разбор Bearer+verifyIdToken,
Docker для локалки. Добавить @aws-sdk/client-s3 + s3-request-presigner (или aws4).

**Безопасный порядок:** Этап1 backend параллельно (не трогая приложение) → Этап2 заполнить
storagePath → Этап3 клиент v1.1 (без ключей, резолвер, cacheKey) → Этап4 выкатка v1.1 → Этап5
ротация (сначала ОТОЗВАТЬ роль старого ключа — обратимо, 24-48ч наблюдать, потом удалить) → Этап6
чистильщик сирот (каскадное удаление объекта и фото чата сейчас НЕ удаляют файлы из S3).
